# 매뉴얼 작성 가이드 (manual-authoring)

Manual은 싱글 프롬프트 Agent의 선택적 서브루틴이다. Agent 본문이 "언제 시작할지"를 결정하고, Manual이 "어떻게 진행할지"를 결정한다. 이 문서는 그 두 층을 각각 어떻게 쓰는지 다룬다. 필드와 연결·참조 규칙은 `manual-data-reference.md`, Agent 전체와 linked 체인 품질 검토는 `manual-review.md`를 참조한다.

## 1. 분리 기준 — 언제 매뉴얼로 빼는가

Manual은 필요한 업무 상황에서만 시작하는 독립 절차다. 대신 진입이 모델의 판단(StartManual 호출)에 달려 있으므로, 시작 시점을 모델 재량에 맡겨도 되는지 함께 판단한다.

| 신호 | 배치 |
|------|------|
| 다턴 수집·검증 루프 (수집 → 복창 → 정정 반복) | **매뉴얼** |
| 조건 판정 상태머신 (영업시간, 자격 판정) | **매뉴얼** |
| 특정 상황에서만 필요한 긴 표기·판별 규칙 (철자 읽기, 전사 아티팩트 판별) | **매뉴얼** |
| 도구 결과에 따라 분기하는 절차 (검색 → 후보 확인 → 재검색) | **매뉴얼** (도구도 매뉴얼에 귀속) |
| 여러 에이전트에서 재사용할 절차 | **매뉴얼** (템플릿 후보) |
| 한 턴으로 끝나는 안내 (가격 안내 멘트, 예약 방법 한 문장) | 본문 유지 |
| 항상 적용되는 톤·가드레일·정체성 | 본문 유지 |
| 진입 자체를 모델 재량에 맡길 수 없는 결정적 강제 (규제·과금 절차) | flow 검토 (→ vox-flow) |

경계 사례: 절차가 2~3문장이면 본문에 둬도 된다. 매뉴얼로 빼는 실익은 절차가 길거나(500자 이상), 상태 분기가 있거나, 본문의 다른 업무와 섞였을 때 오염(규칙 누수·혼선)이 생길 때 발생한다.

### 진입 시점 — 첫 발화는 본문에 둔다

매뉴얼은 통화를 시작하는 장치가 아니라, 기본 Agent가 대화하다가 구체적인 절차가 필요할 때 호출하는 서브루틴이다.

- 통화 시작 직후의 인사, 신원 소개, 용건 확인, 최초 라우팅 질문은 Agent 본문 프롬프트가 담당한다.
- 아웃바운드의 최초 본인 확인 질문도 본문에 둔다. 고객이 답한 뒤 수신자 판정·일정 확인처럼 다턴 절차가 시작되는 지점부터 매뉴얼로 분리한다.
- 고객이 첫 인사 이후 주소·이메일·예약정보를 먼저 말하면, 그 응답 턴에서 해당 매뉴얼을 시작한다.
- 통화 첫 단계부터 반드시 실행돼야 하는 결정적 절차는 매뉴얼보다 본문 또는 flow가 적합하다.

예시:

```markdown
# 본문 프롬프트

첫 발화:
"안녕하세요. 예약 일정 안내로 연락드렸습니다. 예약하신 분 본인이실까요?"

고객이 본인 여부에 답하면 예약 상세를 안내하기 전에
'수신자 판정 및 예약 안내' 매뉴얼을 먼저 시작합니다.
```

## 2. trigger 작성법

trigger는 Manual을 언제 시작할지 판단하는 기준 문장이다. 대화에서 확인된 사실이 trigger 조건에 정확히 맞도록 작성한다.

**진입점 3종을 모두 커버하는 상황 나열형 한 문장**으로 쓴다:

1. **에이전트가 물어봐야 할 때** — 절차가 필요한 업무 국면에 도달한 경우
2. **고객이 먼저 말하기 시작했을 때** — 묻기 전에 고객이 값을 불러주는 경우
3. **기존 값을 확인·정정할 때** — 시스템에 있는 값을 읽어주고 고치는 경우

실전 예 (이메일 수집):

> 고객이 이메일 수령을 선택해 이메일 주소를 물어봐야 할 때, 고객이 이메일 주소를 불러주기 시작했을 때, 또는 등록된 이메일 주소를 읽어주며 확인·정정할 때

진입점 하나만 쓰면 나머지 경로에서 매뉴얼 없이 절차가 시작된다 — 특히 2번(고객 선발화)이 자주 빠진다. 반대로 트리거를 넓게 쓰면("고객이 연락처를 말할 때") 인접 업무에서 잘못 시작된다. 트리거끼리는 상호 배타적으로: 두 매뉴얼의 트리거에 동시에 걸리는 상황이 있으면 모델은 어느 쪽도 확신하지 못한다.

### 시작 발화 예시와 Trigger 중첩 검토

Trigger 문장만 읽고 상호 배타성을 판단하지 않는다. Trigger 초안을 쓴 뒤 각 Trigger에서 실제로 매뉴얼을 시작해야 하는 고객 발화를 2개 이상 만든다. 예시는 짧은 일상 발화와 필요한 정보를 함께 말한 발화를 섞어 실제 통화 표현으로 작성한다.

작성한 모든 발화를 연결할 모든 Trigger에 하나씩 대입한다. 한 발화가 두 개 이상의 Trigger에 동시에 맞으면 Manual 선택이 모호해질 수 있으므로 다음 중 하나로 해소한다.

1. 해당 발화를 하나의 Manual이 소유하도록 Trigger 범위를 명확히 조정한다.
2. 두 절차가 같은 선행 정보와 진행 흐름을 공유한다면 하나의 Manual로 합친다.

발화 예시는 작성·검토 자료다. Trigger 필드나 매뉴얼 content에 예시 목록을 넣지 않는다. 최종 산출물의 설계 요약에는 Trigger별 시작 발화 예시와 중첩 검토 결과를 남긴다.

예시:

| 시작 발화 예시 | 신규 객실 예약 | 기존 예약 변경 | 숙박 편의 요청 |
|---|---:|---:|---:|
| "9월 3일부터 두 명이 묵을 객실 예약을 요청하고 싶어요." | O |  |  |
| "기존 예약을 접근성 객실로 바꾸고 싶어요." |  | O | O |
| "기존 예약에 유아용 침대를 추가하고 싶어요." |  | O | O |

두 번째와 세 번째 발화는 두 Trigger에 동시에 맞는다. 기존 예약의 객실·부가 요청을 `기존 예약 변경`이 소유하도록 `숙박 편의 요청` 범위에서 제외하거나, 두 절차를 하나의 기존 예약 후속 요청 Manual로 합친다.

## 3. 본문 라우팅 계약 — 선응답 누수 방지

트리거 매칭만으로는 부족하다. 첫 발화와 최초 라우팅 질문은 본문에서 수행하고, 대화가 매뉴얼의 구체적인 업무 경계에 도달한 지점에 라우팅 지시를 명시적으로 배선한다. 확립된 패턴:

> 고객이 이메일을 원하면 **고객에게 응답하거나 이메일 주소를 묻기 전에** '이메일 수집' 매뉴얼을 **먼저 시작합니다**. 매뉴얼을 시작하기 전에는 이메일을 직접 묻지 않습니다.

구성 요소 세 가지가 모두 필요하다:

1. **시점 고정** — "응답하거나 묻기 전에". 모델이 먼저 "네, 이메일 주소 알려주세요"라고 말해버리면 매뉴얼 없이 수집이 시작되고, 다음 턴에 시작하면 이미 절차가 어긋난다.
2. **이름으로 지칭** — '이메일 수집'처럼 매뉴얼 이름을 따옴표로. M1 같은 임시 식별자는 본문·content에 하드코딩하지 않는다.
3. **직접 수행 금지** — "매뉴얼 시작 전에는 직접 묻지 않습니다". 필요하면 "'확인해 보겠습니다' 같은 안내도 하지 않습니다"까지 추가한다(판정형 매뉴얼에서 모델이 빈말을 먼저 하는 것을 막는다).

라우팅 지시는 업무 흐름 안의 정확한 위치에 넣는다. "고객이 X를 원하면 → 매뉴얼 시작"처럼 분기 직후에. 본문 말미에 매뉴얼 목록만 나열하는 방식은 시점 고정이 안 돼서 약하다.

이 규칙은 통화 첫 인사 자체를 매뉴얼로 옮기라는 뜻이 아니다. 기본 Agent가 인사하고 용건을 확인한 뒤, 이메일 수집·주소 검증·예약 변경처럼 구체적인 절차에 진입하는 턴부터 적용한다.

## 4. content 구조 — 규칙 + 진행 절차

content는 두 부분으로 나눈다. 검증된 house style:

```markdown
## 규칙
### <원칙 / 표기 규칙 / 판별 규칙 소제목들>
- 항상 적용되는 불변 규칙. 발화 형식, 판별 기준, 금지 사항.

## 진행 절차
### 시작
- 진입 상황별 분기: 어느 상태로 들어갈지 결정.
### <상태 A>
### <상태 B>
### 완료
```

**왜 이 구조인가**: 규칙(불변)과 절차(상태 의존)를 섞으면 모델이 현재 상태와 무관한 지시를 끌어다 쓴다. 분리하면 규칙은 전 상태에 걸쳐 적용되고, 절차는 지금 어느 섹션에 있는지만 추적하면 된다.

### 상태 섹션 작성 규칙

- **고객 상황을 상태로 쓴다**: 상태 이름과 분기 조건은 `current_address_role=collection`, `eligibility_result=review_required` 같은 코드형 할당이 아니라 `회수 주소 확인`, `교환 요청 검토`, `고객이 요청을 철회한 경우`처럼 고객의 의도와 업무 상황으로 표현한다. 모델은 확인한 정보를 대화 맥락으로 유지할 수 있으므로, 대화 절차에 postCall 필드명이나 enum을 반복해서 주입하지 않는다.
- **전이는 명시적으로**: "고객이 동의하면 '완료'로 이동한다", "부정하면 '핵심 주소 추가 확인'으로 이동한다". 섹션 이름을 따옴표로 정확히 지칭한다. 이름을 바꾸면 참조하는 모든 전이 문구를 함께 바꾼다.
- **캐치올 전이를 남기지 않는다**: 각 상태에서 가능한 고객 반응(동의/부정/새 정보/무응답성 반응)마다 갈 곳이 있어야 한다. "남은 후보가 없으면 '추가 확인'으로 이동한다"처럼 소진 케이스도 명시한다. 갈 곳 없는 반응은 모델이 즉흥 처리한다.
- **시작 섹션은 진입점 분기**: trigger의 진입점 3종이 각각 어느 상태로 들어가는지 매핑한다. "이미 완성된 값을 말했으면 '복창 및 확인'으로", "불러주는 중이면 '수집'으로 이동하여 끝까지 듣는다".
- **완료 섹션은 복귀 계약**: ① 확정값을 기록하고(발화용이 아닌 입력용 표기로) ② **매뉴얼 시작 전에 진행하던 원래 요청을 이어서 처리한다**를 반드시 넣는다. 이 줄이 없으면 매뉴얼이 끝난 지점에서 대화가 dead-end가 된다.
- **수집 불가 폴백 상태를 둔다**: 고객이 값이 없거나 불러주기를 거부하는 경우 강요하지 않고 값 없이 원래 업무로 복귀하는 상태('수집할 수 없는 경우')를 명시한다.
- **정정 루프는 부분 재수집으로**: 전체를 다시 받지 말고 "틀린 부분만 다시 받고 그 부분만 복창"으로 좁힌다. 반복 한도는 업무 성격에 따라 명시한다("맞다고 확인할 때까지 횟수 제한 없이").

### 규칙 섹션 작성 원칙

- **발화용 vs 입력용을 분리한다**: 음성으로 읽는 표기(한국어 숫자, "골뱅이", 쉼표 끊어읽기)와 기록·도구 전달용 표기(아라비아 숫자, 영문 주소)를 명시적으로 구분해 각각 예시를 준다.
- **판별 규칙은 질문이 아니라 규칙으로**: 애매함을 고객에게 묻는 대신 판별 기준을 규칙으로 박는다(예: 전사 하이픈은 "하이픈"이라고 단어로 말한 자리에만 실제 하이픈). "그 자리만 질문" 같은 중간 규칙은 실콜에서 루프를 만든다. 질문은 규칙으로 판별 불가능한 소리 겹침(영문 O vs 숫자 0)에만 허용한다.
- **검증은 추측·보정 금지를 명시한다**: 목록 대조 검증(동 목록, 후보 목록)에서는 "비슷한 값으로 추측·보정하지 않는다", "일치할 때까지 완료로 이동하지 않는다"를 명시한다.
- **예시 발화는 따옴표로 완성문을 준다**: 모델이 복사할 앵커. 상황별 예시(현재/미래, 동의/부정)를 각 1개씩.
- **내부 용어 발화 금지**: "복창", "매뉴얼", "검증", 상태 섹션 이름은 내부 용어다. 고객 발화 멘트에 등장시키지 않는다(예: "복창하겠습니다" 대신 "말씀하신 주소 확인하겠습니다").

### 상황형 분기 작성 예시

피해야 할 형식:

```markdown
- request_type=exchange로 기록한다.
- current_address_role=collection으로 변경한다.
- eligibility_result=review_required이면 다음 상태로 이동한다.
```

권장 형식:

```markdown
### 주소 용도 확인

1. 고객이 반품을 원하는 경우 회수할 주소를 확인한다.
2. 고객이 교환을 원하는 경우 다음 두 주소를 구분한다.
   1. 기존 상품을 회수할 주소
   2. 교환 상품을 받을 주소
3. 어떤 주소인지 불분명하면 "회수할 주소인가요, 교환 상품을 받을 주소인가요?"라고 묻는다.

### 교환 요청 확인

1. 고객이 교환을 원하는 경우 교환 사유를 확인한다.
2. 고객이 반품으로 의사를 바꾸면 '반품 요청 확인'으로 이동한다.
3. 교환 가능 여부는 확정하지 않고 담당자 확인이 필요하다고 안내한다.

### 완료

1. 고객이 확인한 요청 유형, 사유, 상품 상태와 주소만 이후 대화에서 사용한다.
2. 실제 승인이나 회수 예약이 완료됐다고 말하지 않는다.
3. 이 절차 전에 진행하던 고객의 원래 요청을 이어서 처리한다.
```

postCall 추출용 필드명과 enum은 postCall 정의가 소유한다. 매뉴얼 content에는 고객 상황과 필요한 행동을 적는다. 정확한 입력 키가 필요한 도구를 호출할 때만 해당 호출 단계에서 필드명을 사용한다.

### Side-effect와 기록

Manual이 값을 수집했다는 사실은 외부 업무가 처리됐다는 뜻이 아니다. 완료 표현은 `voice-ai-playbook.md`의 "처리 근거와 완료 표현" 계약을 그대로 따른다.

- 외부 상태를 바꾸는 쓰기 Tool 성공이 있으면 그 성공 범위까지만 완료 표현을 사용할 수 있다.
- 읽기 Tool 성공은 조회된 사실만 말할 근거다.
- PostCall만 있으면 "요청으로 남기겠습니다"라고 안내한다.
- Tool과 PostCall이 모두 없고 후속 요청을 남기지 않으면 "말씀하신 내용을 확인했습니다"라고 안내한다.
- Tool 결과가 해당 Side-effect의 최종 성공을 명시하지 않으면 완료로 간주하지 않는다. 비최종·조건부·불명확한 결과는 Tool 계약에 정의된 상태까지만 안내한다.
- 담당자 연락·기사 방문·발송처럼 미래 행동도 이를 실제로 예약·배정한 근거가 없으면 보장하지 않는다.

## 5. 도구 귀속

절차 전용 도구(주소 검색 등)는 해당 매뉴얼에 연결해 절차 안에서만 사용하도록 한다.

- **content에서 반드시 `@tool:이름`으로 참조한다.** 호출 지시는 "…값만 채워 @tool:search_address 를 한 번 실행한다"처럼 호출 횟수·입력 조건까지 명시한다.
- 도구 결과의 정확한 필드명은 `### 도구 결과 해석` 같은 내부 규칙 블록에서만 사용한다. 상태 섹션과 전이 문구는 raw enum을 반복하지 않고 "도구가 단일 후보 확인을 권하면 '후보 확인'으로 이동한다"처럼 고객 상황과 다음 행동으로 표현한다. 정확한 필드명·enum을 고객 발화나 상태 이름으로 쓰지 않는다.
- 연결 필드와 `@tool:` 참조 형식은 `manual-data-reference.md`를 따른다.

## 6. linked 매뉴얼 체인

매뉴얼에서 다른 매뉴얼로 이어지는 절차는 후속 Manual을 `linked_manual_ids`에 연결하고 content에서 `@manual:<UUID>`로 참조한다.

- **직접 연결 vs linked 선택**: Agent 본문에서 바로 시작해야 하면 Agent에 직접 연결하고, 특정 Manual의 절차 안에서만 사용하는 후속 절차면 linked로 연결한다. 후속 Manual의 진입 조건은 부모 content에 상황형 문장으로 명시한다.
- 체인이 깊어지면(3단 이상) 절차 추적이 어려워진다. 2단을 기본으로, 그 이상이면 flow 전환을 검토한다.

## 7. 함정 체크리스트

작성·수정 후 아래를 점검한다:

- [ ] 통화 첫 인사·신원 소개·최초 라우팅 질문을 매뉴얼로 옮기지 않았는가
- [ ] 본문 응대에서 구체적인 다턴 절차로 넘어가는 매뉴얼 경계가 명확한가
- [ ] trigger가 진입점 3종을 커버하고, 다른 매뉴얼 트리거와 겹치지 않는가
- [ ] 각 Trigger에서 실제로 시작해야 하는 고객 발화 예시를 2개 이상 작성했는가
- [ ] 모든 시작 발화 예시를 연결할 전체 Trigger에 교차 대입했는가
- [ ] 두 개 이상의 Trigger에 맞는 발화가 있다면 하나의 소유 Manual을 정하거나 절차를 합쳐 중첩을 해소했는가
- [ ] 본문 라우팅 지시가 시점 고정("응답하거나 묻기 전에") + 이름 지칭 + 직접 수행 금지를 갖췄는가
- [ ] 진행 절차가 `key=value` 형태의 상태 할당에 의존하지 않고 고객의 의도와 상황으로 분기하는가
- [ ] postCall 필드명과 enum이 대화 절차에 섞이지 않고, 정확한 필드명은 실제 도구 입력 계약에서만 사용되는가
- [ ] 외부 상태를 바꾸는 완료 표현에 실제 쓰기 Tool 성공 근거가 있는가
- [ ] PostCall만 있으면 “요청으로 남김”, 후속 요청이 없으면 “내용 확인”으로 제한했는가
- [ ] 조회 Tool이나 중간 상태를 쓰기 성공으로 확대하지 않았는가
- [ ] 모든 상태에서 모든 고객 반응의 전이가 명시돼 있는가 (dead-end·즉흥 처리 구멍 없음)
- [ ] 완료 섹션에 원래 요청 복귀 줄이 있는가
- [ ] 매뉴얼 소유 도구가 content에서 `@tool:이름`으로 참조되는가
- [ ] M-id·내부 용어가 본문·content·발화 멘트에 하드코딩되지 않았는가
- [ ] 플레이스홀더 변수가 비어 있을 때의 분기가 있는가 (빈 `{{고객명}}`을 그대로 읽지 않기)
- [ ] 별도 요구가 없다면 매뉴얼 호출음이 `typing`으로 설정됐는가
- [ ] 같은 업무의 템플릿 매뉴얼이 이미 있는지 확인했는가 (이메일 수집·주소 검증·영업시간 확인)
- [ ] `manual-review.md` 기준으로 직접 연결 및 linked Manual 전체를 재귀 검토했는가
